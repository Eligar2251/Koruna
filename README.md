# ЦСБ — Центральная Строительная База

Сайт на Next.js и React с сохранённым оформлением Tilda. У каждой страницы свой файл стилей рядом с React-кодом. Каталог, корзина, заказы и админка работают через серверные API приложения.

## Запуск

Требуется Node.js 20 или новее.

```bash
npm ci
cp .env.example .env
# Заполните SUPABASE_URL и SUPABASE_ANON_KEY в .env.
npm run build
npm start
```

Панель: секретный путь `ADMIN_PATH` из серверного `.env`; `/admin` закрыт. Каталог: `/katalog`. Корзина: `/korzina`.

После получения изменений нужна новая сборка, а не только перезапуск старой:

```bash
git pull origin arena/edb2e7e6-koruna
npm ci
npm run build
# Затем перезапустите запущенный процесс приложения командой вашего хостинга.
# Если запускаете вручную: остановите старый npm start и выполните npm start снова.
```

Десктопные блоки используют безразмерный коэффициент `--csb-scale`. Выражения `scale(calc(100vw / 1200))` и `height: calc(550px * 100vw / 1200)` некорректны: браузер отбрасывает их и блоки могут схлопнуться. Исправление есть в стилях всех страниц и в конвертере `scripts/port-react.py`.

## Подключение Supabase

Для работы сайта нужны **только две переменные**:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
SUPABASE_ANON_KEY=your-anon-key
```

`DATABASE_URL` и пароль Postgres приложению не нужны. `SUPABASE_SERVICE_ROLE_KEY` для каталога, загрузки фото, заказов, входа и назначения администраторов тоже не нужен. Нельзя подменять им anon key.

Клиент Supabase создаётся на сервере с anon / publishable key. После входа используется JWT пользователя Supabase Auth; доступ к изменениям разрешают RLS-политики и запись пользователя в `admin_users`. Ключи из окружения не передаются в клиентский JavaScript; не добавляйте их в `NEXT_PUBLIC_*`.

Если Supabase вообще не настроен, доступен локальный режим предпросмотра: данные в `data/`, фото в `uploads/`. Эти каталоги не попадают в git. Это не подключение к вашей базе Supabase.

### Подготовка базы и первого администратора

Миграции в `supabase/migrations/` выполняются по порядку через **Supabase SQL Editor** — строка подключения базе для этого не нужна:

1. `20261017120000_clean_database.sql` — необратимая очистка `public`. **Только для первоначальной очистки, не повторять на заполненной базе.** Файлы Storage и пользователей Authentication не удаляет.
2. `20261017120100_catalog.sql` — категории, товары, `admin_users`, бакет фото.
3. `20261017130000_harden_catalog.sql` — права доступа и RLS.
4. `20261017140000_orders_staff.sql` — заказы и назначение администраторов.
5. `20261017140100_seed_catalog.sql` — базовые категории и товары.
6. `20261017150000_inventory.sql` — остатки, неизменяемый журнал складских операций и статусы заказов. Не очищает данные; для существующей базы выполните только эту новую миграцию, если предыдущие уже применены.

Если база уже развёрнута, выполняйте только ещё не применённые миграции. Не запускайте очистку ради обновления сайта.

Первого пользователя создайте в Supabase → Authentication → Users (с подтверждённой почтой), затем назначьте его администратором в SQL Editor:

```sql
insert into public.admin_users (user_id)
select id from auth.users where email = 'admin@example.ru'
on conflict do nothing;
```

После этого входите по секретному пути `ADMIN_PATH` с его почтой и паролем. Новых администраторов назначает существующий администратор из панели. Создание пользователей использует Supabase Auth sign-up: проект должен разрешать регистрацию; если включено подтверждение почты, новому пользователю нужно его пройти. Пароли обрабатывает Supabase Auth, а не service role.

Фото в Supabase загружаются в бакет `product-images` под JWT администратора. Анонимный ключ не даёт права изменять каталог, читать заказы или список администраторов.

### Сохранённые инструменты очистки

Существующие скрипты очистки сохранены. Они не запускаются при старте приложения, сборке или миграции автоматически.

- Для очистки SQL-схемы без строки подключения используйте `supabase/clean.sql` в SQL Editor. Это разрушительная операция, не обычное обновление.
- Для удаления файлов Storage через API нужен отдельный серверный `SUPABASE_SERVICE_ROLE_KEY`. Только для этой ручной операции можно временно задать его в окружении и вызвать `npm run clean -- --storage-only --dry-run`; удаление требует отдельного подтверждения `--yes`. Не удаляйте строки `storage.objects` напрямую: файлы останутся в S3.
- Старый режим очистки через прямое соединение Postgres остаётся в утилите для совместимости. Он не является настройкой сайта и не нужен при работе через SQL Editor. Не добавляйте его реквизиты в окружение приложения.

Не публикуйте реальные ключи, пароли и `.env`.

## Первый вход и восстановление доступа

Ранее указанный `admin@csb.local` не является автоматически создаваемым пользователем Supabase. Универсальный пароль в приложении отсутствует; скрытого обхода Supabase Auth нет.

В локальном режиме (без настоящих реквизитов Supabase) создайте администратора на сервере:

```bash
npm run admin:create -- --email admin@csb.local
# Пароль вводится скрыто. Сброс существующего локального пароля:
npm run admin:create -- --email admin@csb.local --reset
```

Команда не хранит пароль открытым текстом. Нужен постоянный диск `data/` для сохранения локальных учётных записей и секретов сессии при перезапусках. В репозиторий эти данные не включаются.

С настоящими `SUPABASE_URL` + `SUPABASE_ANON_KEY` команда работает с Supabase Auth и выводит SQL для назначения первого администратора. Выполните этот SQL самостоятельно в SQL Editor и подтвердите почту, если этого требует проект. Используйте реальный адрес почты. Альтернатива — создание пользователя через Supabase Dashboard, как описано выше. Сброс пароля Supabase выполняется в Authentication, не локальным `--reset`. Для этой настройки service role и строка Postgres не нужны.

## Панель, склад и оформление заказа

- Товары: добавление, редактирование, фото, цены, категории, публикация, поиск и фильтр.
- Категории: добавление, изменение названия, адреса, порядка и видимости.
- Заказы: состав, контакты, адрес и комментарий; статусы «Новый», «В работе», «Завершён», «Отменён».
- Склад: приход, списание и корректировка **изменения** остатка (не абсолютного значения), основание операции и журнал последних 200 движений. `Не учтён` означает отсутствие начального остатка; внесите его операцией прихода. Отрицательные остатки запрещены. В Supabase операция выполняется атомарно с блокировкой строки товара и проверкой прав администратора. Менять остаток напрямую через обычное редактирование товара нельзя.
- Оформление заказа не резервирует и не списывает остаток автоматически. Проверяются текущие цены и доступное количество; менеджер подтверждает наличие, а при отгрузке проводит списание с номером заказа в основании. Это предотвращает неожиданное списание из-за спама в публичной форме; гарантированного резерва между заказами нет.
- Позиции с неизвестной ценой уточняются менеджером. Стоимость доставки и онлайн-оплата не включены.

Для локальной автоматизированной проверки можно передать пароль в stdin с `--password-stdin` (вместе с `--email`). Не передавайте реальные пароли в аргументах командной строки, не публикуйте их в логах.

## Настройки, заявки и документы

Новая **недеструктивная** миграция: `supabase/migrations/20261017160000_site_operations.sql`.
На существующей базе выполните её после предыдущих миграций в SQL Editor. **Не запускайте повторно очистку базы**.
Используются только `SUPABASE_URL` и `SUPABASE_ANON_KEY`; сервер работает с пользовательской сессией администратора, без service role и строки подключения.

В закрытой панели добавлены:
- **Настройки сайта**: контакты, адрес и инструкции проезда, часы работы, полное юрлицо, банковские реквизиты, тексты исходных страниц и изображения (включая логотип, фоны и категории). Фото загружаются как JPEG/PNG/WebP до 5 МБ; проверяется сигнатура. Внешние произвольные URL не разрешаются. Изменения видны после обновления открытых страниц. Защита версии предотвращает перезапись настроек из старой вкладки.
- **Массовый редактор**: до 100 выбранных товаров, все редактируемые поля каталога, индивидуальные/общие фото, наличие и публикация, подготовка общего изменения, JSON-экспорт/импорт `{id, patch}`. Перед сохранением нужно проверить таблицу и подтвердить пакет. При ошибке весь пакет откатывается. Количественные остатки меняются только через складской журнал. Загруженное фото ещё не означает сохранение строки; сохраните пакет. Неиспользованные загруженные объекты при необходимости удаляются оператором через Storage API.
- **Заявки и заказы**: общий список и счётчик автоматически обновляются; защищённый SSE передаёт снимки при изменениях (опрос базы раз в 3 с), переподключается и при недоступности переключается на опрос раз в 5 с. Настройте reverse proxy без буферизации для `/api/admin/orders/events`, таймаут не менее 60 с. Список ограничен последними 1000 обращениями.
- **Браузерные уведомления**: включаются явно кнопкой с запросом разрешения, только в поддерживаемом браузере/HTTPS. Текст без имени/телефона клиента. Работают, пока панель открыта; это не push для закрытого браузера. При отказе разрешения заявки остаются видны в панели. Для разрешений внутри iframe может понадобиться открыть сайт отдельной вкладкой.

Формы «Получить цену», «Получить расчёт» и обратная связь открывают единую заявку. Карточки ведут в соответствующие разделы; поиск и сортировка находятся в каталоге. Внешние карты не загружаются: на контактах показаны адрес, копирование, телефон и условия доставки; собственную схему можно загрузить в настройках. Старые неработающие виджеты Tilda (корзина, поиск, cookie) удалены, используется React-корзина и единое уведомление.

### Перед приёмом персональных данных

**По умолчанию приём заявок/заказов выключен.** В настройках заполните юридический адрес, контакт по ПД, фактическую первичную базу в РФ, обработчиков/места обработки и сроки хранения. Проверьте документы `/privacy`, `/soglasie`, `/cookies`, затем подтвердите готовность оператора и сохраните настройки. Во всех формах отдельный обязательный чекбокс согласия изначально снят. С обращением сохраняются дата/время, оператор, цель и версия; после изменения настроек устаревшие формы требуют обновления. RLS требует согласие и текущую ревизию настроек. Старые заказы остаются доступны.

Сайт использует только необходимые cookie сессии администратора и localStorage для корзины/выбора уведомлений, без аналитики, рекламы, внешних карт и пикселей. Cookie-баннер можно открыть повторно из подвала. Это **техническая основа, а не гарантия соответствия 152-ФЗ**: оператор отвечает за реальное местоположение БД, договоры/поручения, необходимые уведомления Роскомнадзора, условия трансграничной передачи, правовые основания, меры защиты и регламент удаления. Смена текста «место хранения» не меняет регион Supabase. Перед запуском требуется проверка фактической инфраструктуры и документов; автоматического удаления по произвольному текстовому сроку нет.

Локальные JSON-хранилища пригодны только для одного процесса на постоянном защищённом диске. Не размещайте production-заявки в эфемерной файловой системе/serverless и не публикуйте `data/` или `uploads/` в Git. Для нескольких инстансов используйте настроенную базу и Storage. Делайте защищённые резервные копии и выполняйте удаление ПД по регламенту оператора, включая копии.

Проверка: `npm test` (в том числе новая миграция в изолированной PGlite, RLS, атомарность пакета, согласие, конфликты настроек), `npx tsc --noEmit`, `npm run build`. Конвертер `scripts/port-react.py` вызывает `scripts/enhance-react.py`, сохраняя React-обработчики, конфигурацию и исправления изображений при повторной генерации.

### Навигация и скорость переходов

Шапка теперь общая и сохраняется между страницами в корневом layout. Внутренние переходы используют Next.js Link без перезагрузки документа; предварительная загрузка происходит по наведению/фокусу, а не массово для всех карточек. Меню каталога на React поддерживает мышь, клавиатуру, Escape и отдельную кнопку раскрытия на мобильном. Разделы берутся из опубликованных категорий; у листовых материалов и утеплителя сохранены вложенные разделы. Фильтры каталога: категория, диапазон цены, поиск, наличие и сортировка; есть сброс.

Публичные настройки и каталог кэшируются на сервере на 30 секунд, сбрасываются после успешного редактирования в админке. Запросы категорий и товаров выполняются параллельно. Сессии, складские операции, заявки и проверка заказа при оформлении **не кэшируются**. Изображения карточек загружаются лениво, без блокировки переходов. Быстрые переходы не отменяют зависимость первого запроса от скорости БД/хостинга и сети.

Подставленные изображения каталога заменены исходными фотографиями из `main`; сохранены прежние пути `/assets/catalog/*`, поэтому исправление действует и на существующие строки товаров, ссылающиеся на них. Для 20-пиксельных превью архива используются доступные полноразмерные фотографии того же экспорта, без генерации новых изображений. Настройки загруженных оператором фото и сами товары не перезаписываются.

На странице «О компании» убраны подписи-заголовки видео и переработана сетка в прежней зелёно-белой стилистике. Сохранены исходные ID видео; внешний Kinescope-плеер запрашивается только после отдельного нажатия, о передаче технических данных посетитель предупреждён. Эти сведения нужно учитывать оператору в документах и перечне обработчиков. При регенерации `enhance-react.py` дополнительно вызывает `refine-site.py`, сохраняя общую шапку, Link-переходы, фотографии и новую галерею.


## Приём расчётов, почта и закрытая панель

1. На существующей БД выполните **только добавочную** миграцию `20261017170000_staff_roles_mail.sql` (после предыдущих миграций). Не повторяйте очистку. Первый существующий администратор становится владельцем. На новой БД первого владельца создают через `npm run admin:create -- --role owner` и SQL, который выводит CLI для Supabase. Подключение БД по-прежнему только URL + anon key.
2. Выполните `npm run admin:setup`: в игнорируемом `.env` появятся `ADMIN_PATH` (непредсказуемый путь из 32 случайных байт) и `JWT_SECRET` (ключ не менее 32 символов). Команда не печатает секреты, сохраняет существующие значения и старый файловый JWT-ключ. На продакшене задайте эти переменные в секретах хостинга; в нескольких инстансах значения должны совпадать. Не помещайте их в `NEXT_PUBLIC_*`. Перезапустите сервер. Адрес смотрите только в своём `.env`.
3. Без правильной конфигурации панель **закрыта**. `/admin`, варианты кодирования адреса и API без подписанного gate-cookie возвращают 404. Секретный URL выдаёт HttpOnly / SameSite=Strict gate JWT на 12 часов; для данных нужен **отдельный вход с паролем**, актуальная роль в БД и JWT-сессия. Включены noindex, private/no-store, no-referrer. На HTTPS cookie Secure. После истечения gate нужно повторно открыть секретный адрес. При ротации ADMIN_PATH старые gate-cookie становятся недействительны. При ротации JWT_SECRET локальные JWT-ключи паролей необходимо переподписать/сбросить через CLI; Supabase Auth хранит свои пароли независимо.
4. Владелец добавляет администраторов и владельцев, меняет роли. Администратор добавляет только администраторов. Последнего владельца понизить нельзя. Проверки есть в API, локальном store и SQL RPC; передача `role=owner` в клиенте не повышает права. Если Supabase требует подтверждение почты, новый сотрудник должен подтвердить её перед входом.
5. Задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` (пароль приложения), `MAIL_FROM`. Например, российский SMTP-провайдер, порт 465 + TLS либо 587 + обязательный STARTTLS. `REQUESTS_EMAIL` — получатель; если не задан, используется email сайта. Адреса назначения не берутся из формы посетителя. Сертификаты TLS проверяются. Пароль SMTP не попадает в публичные настройки, ответы API или логи. После изменения env перезапустите сервер.
6. В панели → «Настройки сайта» проверьте почту кнопкой **«Отправить тестовое письмо»**. Затем заполните реальные реквизиты оператора, места хранения/обработки и политику и включите приём форм. Юридические сведения не выдумываются, согласие не проставляется автоматически. По умолчанию приём остаётся выключенным, пока оператор не завершит настройку.
7. В расчёте и корзине общий ввод телефона `+7 (999) 123-45-67`; сервер принимает только полный российский номер и сохраняет его в `+79991234567`. Заявка сначала надёжно сохраняется, затем отправляется письмо. SMTP-сбой **не удаляет заявку** и не заставляет посетителя создавать дубль. В «Заказах» видны статусы почты: ожидание, SMTP не настроен, ошибка, принято сервером. Есть защищённая повторная отправка; подтверждённо отправленное письмо не отправляется повторно, зависшая попытка доступна повторно через две минуты. При обрыве между приёмом письма SMTP-сервером и сохранением подтверждения повтор может дать дубль — распределённую отправку нельзя гарантировать exactly-once. Доставка не имеет фонового cron: после сбоя повтор запускается администратором. Принятие SMTP-сервером не гарантирует попадание во «Входящие»: настройте SPF/DKIM/DMARC у своего провайдера.

Скрытый путь — дополнительный барьер, **не шифрование и не замена авторизации**. JWT подписан, а не зашифрован. Не публикуйте путь, исключите его и cookie из access-логов/аналитики, используйте HTTPS и доверенный reverse proxy (не принимайте произвольный `X-Forwarded-For` от клиента). Абсолютной недоступности «для всех» скрытым URL добиться нельзя.

Golos Text российской Paratype поставляется локально, с кириллицей и OFL-лицензией (`public/assets/fonts/golos-text/`). Внешних запросов к шрифтовым CDN нет. Источник файлов — открытый репозиторий проекта, явно указан в `SOURCE.md`; непосредственное скачивание с .ru в этой среде недоступно.


### Если после настройки панели возвращается 404

Старая версия `admin:setup` игнорировала `KEY=VALUE` после команды и принимала только пути длиной от 32 символов. Обновлённая версия читает аргументы и допускает один путь `/` + 16–128 символов (`A–Z`, `a–z`, `0–9`, `_`, `-`). Полный URL с доменом в `ADMIN_PATH` не нужен. Проверка JWT остаётся строгой: минимум 32 символа.

После обновления кода, например:

```sh
node scripts/setup-admin-entry.mjs --path /your-new-private-panel --rotate-secret
npm run admin:check
npm run build
# Затем перезапустите именно работающий сервер / PM2 / контейнер.
```

Вместо `--path ...` можно использовать `--rotate-path` для генерации непредсказуемого адреса. Секрет и адрес смотрите в локальном env-файле, не публикуйте их. Переданный в чат секрет/адрес считайте раскрытым. Не передавайте сам JWT-ключ в аргументах: npm и история терминала могут его записать.

Теперь `npm run admin:setup -- ADMIN_PATH=/your-new-private-panel` и POSIX-переменные **перед** командой тоже поддерживаются. Без `--rotate-secret` существующий корректный ключ сохраняется. Ошибочные аргументы/значения отклоняются **до записи** с понятным сообщением, а не молча игнорируются.

`admin:check` не меняет файлы и не выводит секреты. Он учитывает приоритет Next.js для production: окружение процесса → `.env.production.local` → `.env.local` → `.env.production` → `.env`. Setup обновляет файл, из которого реально берётся каждый ключ. Для dev используйте `node scripts/setup-admin-entry.mjs --check --mode development`. Если внешний env хостинга/службы перекрывает новый ключ, скрипт остановится: исправлять нужно настройки окружения этого хостинга, а не только файл.

Проверка CLI не проверяет переменные **уже запущенного** процесса: после изменения файлов/окружения обязательно перезапустите приложение и убедитесь, что развёрнута новая версия кода. Открывайте свой домен + `ADMIN_PATH`; `/admin` намеренно остаётся 404.

При ротации JWT и наличии локальных учётных записей setup остановится, чтобы не сломать вход молча. Сделайте резервную копию; только для осознанного сброса добавьте `--allow-local-password-reset`, затем восстановите локальные пароли через `npm run admin:create -- --reset`. Пароли Supabase Auth от JWT_SECRET сайта не зависят.


### Windows / PowerShell: npm поглотил флаги или не найден dotenv

Требуется Node.js **20.12+** (рекомендуется актуальная LTS). Настройка больше не импортирует npm-пакеты: для env используется встроенный парсер Node. Она работает и до `npm ci`, отдельно от зависимостей Next.js. `npm ci` всё равно нужен после обновления зависимостей самого сайта.

Вместо передачи флагов через npm используйте отдельную команду:

```powershell
npm ci
npm run admin:rotate
npm run admin:check
npm run build
```

`admin:rotate` уже содержит `--rotate-path --rotate-secret` в `package.json`, поэтому PowerShell/npm не должны передавать их снаружи. Альтернатива, полностью минуя npm:

```powershell
node scripts/setup-admin-entry.mjs --rotate-path --rotate-secret
node scripts/setup-admin-entry.mjs --check
```

Если нужны другие параметры, передавайте их напрямую `node scripts/setup-admin-entry.mjs ...`. Не передавайте JWT-ключ в командной строке. При обнаружении проглоченных npm-флагов скрипт останавливается **до изменения файлов**, вместо тихого запуска без ротации. Сохраняется защита локальных паролей при ротации ключа.

После сборки остановите прежний процесс и запустите сайт заново (либо перезапустите службу/PM2/контейнер). Адрес — домен сайта + `ADMIN_PATH` из env-файла, не `/admin`.
